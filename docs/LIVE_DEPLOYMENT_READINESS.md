# Live Operations deployment readiness

Live Operations is suitable for a **controlled private pilot** after the operator completes the steps below. It is not ready for an unrestricted public self-service launch. The local verification covers the application and a disposable PostgreSQL database; it does not verify a production host, external merchant accounts, backups, or failover.

## Before exposing a pilot

1. Restrict access to the web and API with a private network or an authenticated HTTPS reverse proxy. The Compose ports bind to localhost. The [single-host Caddy example](../deploy/Caddyfile.live.example) protects the UI and API with a pilot password and lets only signed provider webhook POST paths reach the API without that password. Keep PostgreSQL inaccessible from the public network.
2. Set `POSTGRES_PASSWORD` to a random URL-safe value and `SESSION_SECRET` to a separate random value of at least 32 characters. Set `CREDENTIAL_ENCRYPTION_KEY` to a backed-up Fernet key before entering provider credentials. Never use the Compose development defaults on a host reachable by other users.
3. For the single-host Caddy example, set `NEXT_PUBLIC_API_URL=https://pilot.example.com/api` and both `CORS_ORIGINS` and `FRONTEND_URL` to `https://pilot.example.com`, replacing the example host. The pilot Compose override sets `COOKIE_SECURE=true`. The public API URL is embedded in the web build, so rebuild the web image if it changes.
4. Set `SHOPIFY_REDIRECT_URI` to the external HTTPS API callback URL if Shopify is enabled. Register the same callback and webhook URLs with the provider. Configure Razorpay's webhook URL and matching secret in Integrations. Keep `PUBLIC_SHOWCASE=false` for a Live pilot.
5. Provide PostgreSQL backups and a restore test, retention for source records and demo runs, log collection, resource limits, and a restart/alert policy. Rotate secrets through a planned process; losing the credential encryption key makes stored provider tokens unreadable.

Set `PILOT_HOST=pilot.example.com` for Caddy and generate a hashed pilot password with `caddy hash-password`; store its result as `PILOT_BASIC_AUTH_HASH` in Caddy's environment. Put the [Caddy example](../deploy/Caddyfile.live.example) on the host, then start all four services with `docker compose -f docker-compose.yml -f deploy/compose.live.yml up -d --build db api sync web`. This override requires the pilot secrets and HTTPS origins, enables secure cookies, and adds restart policies and API/web health checks. Check `docker compose -f docker-compose.yml -f deploy/compose.live.yml ps`, the protected HTTPS `/api/health` endpoint, the `/live` page, and the `sync` logs. The scheduler is required for periodic provider reads; manual **Sync now** works independently. Test account creation, sign-in/out, a small CSV preview and import, source inspection, incident review, a scenario, replay, and the printable receipt on the actual HTTPS domain. Test provider OAuth, API reads, and signed webhooks with authorized development or test merchant accounts before relying on provider data.

## Current verification boundary

- The local API suite, PostgreSQL runtime checks, web build and browser journeys are recorded in [Validation and limitations](VALIDATION_AND_LIMITATIONS.md). Provider adapter and webhook tests use simulated external responses. No real Shopify installation or Razorpay merchant delivery has been verified.
- The default stack does not supply HTTPS, managed secrets, edge registration controls, distributed rate limiting, backup/restore, retention, monitoring or failover. These are release requirements for a public self-service launch.
- The Scenario Lab can use a deterministic seven-day per-SKU order rate and observed order quantities when a snapshot contains at least eight recent SKU orders across three days. It exposes source order IDs, the model version, coverage, and the resulting schedule. The comparison and verification replay the same modeled inputs across all three branches. The historical backtest still evaluates aggregate order volume; it does **not** validate the new per-SKU model. Treat modeled demand as a scenario estimate until SKU-level historical evaluation is available. With insufficient SKU order items, use manual demand.
- The optional LLM handles evidence-backed incident investigation only; it does not calculate inventory, demand, revenue, or policy outcomes. A real pilot inference check requires configured model credentials and a saved `ai_enabled` trace with passed validation. No external inference was verified in the local stack. Scenarios are hypothetical and never write to merchant systems. Replay starts at first ingestion. Older observations can be loaded in pages of 500.
